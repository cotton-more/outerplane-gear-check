and the [Wiki](https://github.com/cotton-more/outerplane-gear-check/wiki) (guide in two languages).

## Commands

All commands are in `Taskfile.yml` (requires [go-task](https://taskfile.dev): `brew install go-task`), list — `task --list`:

```bash
task setup        # npm ci
task dev          # dev server with hot reload; data — docs/'s outerpedia commit built by the current update.py (dev:data), images from docs/
task test         # type check + tests
task build:pwa    # PWA site in docs/ with fresh outerpedia data — manual publishing step
task build:single # standalone page outerplane-gear.html (+ build/artifact.html)
task check        # check the built docs/ against the published one (same as the site bot does)
task preview      # site as on Pages at http://localhost:8000: current code on data from docs/ (in build/preview)
task screenshots  # retake screenshots for README and Wiki, both languages (needs Chrome)
task tour:check   # run the tutorial tour in Chrome at four sizes (Screen sizes) and two themes, frames — build/tour-check/
task publish      # pull main → tests → docs/ → checks → commit → push → wait for Pages deploy
```

Viewing changes before pushing:

- `task dev` — for working on code: hot reload. Its data: `task dev:data` (`update.py --dev-data build/dev-data.json`) builds the
  dataset of the outerpedia commit in `docs/index.html` with the current `update.py` — only when `update.py` or `docs/` changed,
  needs the network; so a new data field (as `Char.chc`, `mainValues`) shows before a publish. The server log says which data
  it took (`[ogc] данные: …`); no file or another commit — `docs/`'s data, as before;
- `task preview` — the site exactly as the bot will deploy it after push: current code on the same data as in `docs/`,
  with service worker and offline mode. Builds a copy in `build/preview` (`update.py --same-data`), does not touch `docs/`.

`task build:pwa` writes to `docs/` — this is the manual publishing step ([PUBLISH.md](PUBLISH.md)). Do not commit a `docs/` built this way
together with code: the bot will see "site already built from this code" and skip its checks, and fresh outerpedia data
will reach the site bypassing the PR. Also, after the push the bot commits its own `docs/` build, and `git pull --rebase` will refuse
with a modified `docs/`. Changed your mind about publishing — `git restore docs`.

## Build and data updates

The build has two steps: `vite build` builds the app into `build/app/index.html`, then `update.py` injects
data and emits three formats. The Taskfile does both steps. The site is updated by the bot in GitHub Actions (push with code
changes — immediately, new data — via PR) or by `task publish` from this machine — details in [`PUBLISH.md`](PUBLISH.md) and [`AUTOUPDATE.md`](AUTOUPDATE.md).
The PWA is a function only of code and the data snapshot: the data date is the outerpedia commit date, not build time. The **snapshot**
(outerpedia commit in «Ещё» → «О приложении» (More → About) and the data version in `sw.js`) moves only when new data changes what the
current code builds: when outerpedia has a new commit, `update.py` rebuilds the published commit with the same code and compares
the sets; if they match (changes were in files we don't use or fields we don't read) — the snapshot stays. So if data and code haven't
changed, the build is byte-identical: no extra commits, and a code-only change yields a new app version without the
«Вышли новые данные» (New data is out) banner. On Linux (Actions) the build is the same as on Mac.

The script takes the latest outerpedia commit from GitHub, rebuilds the page and prints what changed:
new and removed characters, updated builds, renames, new items and sets. The PR report (`scripts/check-data.mjs`
`buildChanges`) also says what changed inside each updated build.
New characters are marked on the page with a NEW badge. Roster and settings in the browser are preserved.
If outerpedia changes its data format and some recommendations fail to match, the script reports this separately.
If the GitHub API is unavailable (limit 60 requests/hour) or the published snapshot for comparison failed to download, the PWA
is not built: otherwise there's no way to tell whether data changed, and phones would get a false «Вышли новые данные» banner.

`update.py` flags are passed after `--`, e.g. `task build:pwa -- --ref <sha>`:

- `--source ~/path/to/outerpedia` — take data from a local clone instead of downloading;
- `--ref <sha>` — pin a specific commit;
- `--same-data` — with `--pwa DIR`: same outerpedia commit as already in `DIR/index.html` — rebuild code only
  (this is how `task preview` builds);
- `--no-embed` — don't embed icons in the standalone page (file ~0.5 MB instead of ~2.3 MB, but icons need internet);
- `--refresh-images` — re-download icons, ignoring the cache;
- `--out path.html` — write the standalone page elsewhere (the publishing variant goes next to it as `path.artifact.html`);
- `--dump-json data.json` — additionally save the dataset as JSON;
- `--report-json report.json` — build summary for checks: changes, warnings, unmatched recommendations,
  whether the data snapshot moved (`dataChanged`, why — `snapshot`) (`task build:pwa` writes it to
  `build/data-report.json`, `task check` reads it, the bot uses `dataChanged` to decide whether there's anything to propose in a PR).

Regular data updates and code publishing on push are done by GitHub Actions — [AUTOUPDATE.md](AUTOUPDATE.md). The outerpedia commit sha request
uses `GITHUB_TOKEN` from the environment if present (in Actions — higher API limit).

**App version in «Ещё» → «О приложении»** — date and hash of the last commit that changed code (`src`, `index.html`,
`vite.config.ts`, `package.json`, `update.py`, `pwa`); injected by `vite.config.ts`. Not build time and not HEAD:
publishing commits data, otherwise every rebuild would change the page — phones would download a new version without
a single change. Built with uncommitted changes in these paths — the string carries a marker.

**Updating on the phone** (`src/app/usePwa.ts`). `sw.js` has two versions: `VERSION` — hash of all site files (new
app version on any change), `DATA` — outerpedia snapshot commit. The new service worker waits; the page queries
it (`ogc:info` via `MessageChannel`) and compares `DATA` with its own `meta.commit`. Different — «Вышли новые
данные» banner with «Обновить» (Update). Same, no response (sw.js from earlier releases), or the page has no commit — only the
app was updated: at the top of «Ещё» «Готова новая версия» (A new version is ready) with «Обновить», and if the worker was already waiting at
page load (cold start), the page activates it itself and reloads — the item in the form is in `ogc.item`.
Mid-work an app update also switches on by itself at a quiet moment (owner, 2026-10-15: in split screen the app is
never cold-started or hidden, so it never updated): the page went to the background, or 10 s without a tap with no
substat on the form, no sheet or dialog (`[role="dialog"]`), no «Вернуть» message and no focused input (App's `quiet`);
never during a tour. New data still waits for the banner. The page asks for a new version every 30 min while visible,
and on coming back to it.
`sw.js` precaches with `Cache.addAll`, which rejects duplicate requests and fails the whole install — the file list
must stay unique (`update.py` and the worker both dedupe; 2026-10-14 two shared portraits stopped every update).
Don't change the `'skipWaiting'` string in `sw.js`: pages from earlier releases send it too.

## `src/` layout

Code is organized by feature: a folder is what the player sees, not a technical layer. Dependencies go only downward:
`shared` → `game` → `features` → `screens` → `app`. Features are ordered `eval` → `gear` → `ingame` → `roster` → `worn` → `tryon` →
`trade` → `batch` → `team`: each takes (both logic and markup) only from those to its left. Where a lower feature would display a higher one (form
and verdict — gear rows and hero mode), it's a screen — `screens/`. `i18n` and `tour` are cross-cutting. The rule is enforced by
`test/layers.test.ts`. Imports from another folder — from root, `@/features/gear/pool`; from own folder — `./x`.

## Screen sizes

The app is built and checked for the owner's devices only (owner, 2026-10-15; nobody else's devices are known):

| Where | Window | `task tour:check` |
|---|---|---|
| computer (daily use: the game on the phone, the app here) | 2056 × 1202, and 1280 × 800 for a laptop | ✓ both |
| Pixel 11 Pro split with the game, stacked | 411 × 564 (426 × 586 at «Max» resolution) | ✓ |
| the same, side by side | 411 × 363 (437 × 378) | ✓ |

- **Width.** Nothing is laid out narrower than `MIN_W` = 410 (`shared/layout/useLayout`): a narrower window shows the same page
  laid out at 410 and scaled down with `zoom` (smaller text, no sideways scroll). So there are no `max-width` media rules
  under 410 — don't add any. Steps above it: `narrow` < 720 (phone layout, verdict bar at the bottom), `xs` < 560,
  `sheet` < 900, `wide` ≥ 1100. At 2056 the page is a centred 1240 px column (`.app`).
- **Height.** One step: a window up to `SHORT_H` = 480 is short (the side-by-side split); every short-window CSS rule is
  `@media (max-height: 480px)` and `layout.tall` is its opposite (tutorial and tips are offered only when tall). Keep the
  step away from the real heights (363–378 and 564–586).
- A layout change to the form, the verdict or the tour — `task tour:check` (both tours at these four sizes, both themes).

## Tests

The evaluation logic is guarded by the golden `test/golden.json`: 800 deterministic cases and 80 input panel lists.
It was originally captured from the old page (before the React migration) — `scripts/golden-old.mjs`. Intentionally changed
behavior — `task golden:update` and review the golden diff: it shows exactly the cases that changed.
The `golden:update` run itself prints differences from the old file — that's normal, the file is already overwritten.

The golden and unit tests run on the frozen `test/fixtures/data.json` (outerpedia a31f580; fields `mainBlocks`, `mainValues`,
`fixedMains`, `fixed` and `bonus` on sets and items, `fusionOf`, `spd`, `chc`, `eff`, `spdUp` and `turn` on characters, `bosses` were added by the same `update.py` from the same commit), so fresh
outerpedia data is guarded by a separate check — `scripts/check-data.mjs` (`task check`, site bot): the built page
in jsdom, the same
golden inputs on old and new data, "every build finds its piece". What exactly is checked — in
[AUTOUPDATE.md](AUTOUPDATE.md).

Unit tests cover rules that are easy to break silently: state and its persistence (`appState`), armor (`armor`:
Epic strictness, chain positions with combos, "0–1 needed stats — always dismantle" by brute-forcing all combinations),
"not in the list" (`unlisted`), item code (`itemCode`), main rows (`mains`: what is forbidden in the grid and when
main takes a place in the chain).

Tests live in `test/` in the same folders as the code (`test/gear/`, `test/trade/`…); at the root — golden, `i18n` and
fixtures. They can't move into `src`: tests contain Russian phrases, and `test/i18n.test.ts` forbids them in `src`. The layout
is guarded by `test/layers.test.ts`: every file in its folder, imports only downward through layers and in feature order.

**The owner's real data never goes into `test/`** (the repo is public). The owner's snapshot (`.x/00-equip.md`, with its siblings
`.x/00-roster.md` and `.x/00-notes.md`, outside git) is read at runtime by `test/trade/helpers.ts` (`hasOwner`, `loadOwner`);
tests that use it (X1, X5, X6) are `it.skipIf(!hasOwner())` and skip silently without the file. Probes on real data live in
`build/` or in the owner's working folder outside git, never in the tests.

Phrases — only in `src/i18n`: the golden compares Russian texts verbatim, and `test/i18n.test.ts` checks the English version —
all golden cases in English without a single Cyrillic letter, and no Russian phrases in code bypassing the dictionary. New phrase —
key in `ru.ts` and in `en.ts` (TypeScript won't compile without the second). **Game words stay English in the Russian UI**: the game

## Storage and URLs

State, roster, language, partially entered item and completed tutorial (`ogc.tour`) are in localStorage with the `ogc.` prefix; keys and the field subset
are compatible across versions, unknown roster ids are not erased. The link `…/#demiurge-stella` opens a character, `…/#OGH…` — the shared hero card (the code is read before
`useHashRoute` rewrites the URL; it doesn't stay in the URL, nothing is written to storage).
If the browser opened the page in «Версия для ПК» (Desktop site) mode, `useLayout` detects it via `screen.width` and returns the
mobile layout.

Character list: `ogc.state.cOwned` — «Мои» mode (true; «Доодеть» after restart is also «Мои»), false — no mode pressed, every hero
with builds (there is no «Все» button any more: a second tap on the pressed mode releases it; internally `cMode: 'all'`); the old
`cAll` ("show also without builds") is neither read nor written. While the roster is empty, no mode is pressed (`charMatches` doesn't
substitute the mode — that's done by the list, `openCharAction` and `App`, which writes `'all'` while the roster is empty), and the first
star doesn't change it. Element and class (`cel`, `ccl`) are remembered, search is not. `ogc.gameIcons` — icons; no
entry — game icons.

`ogc.trade` — the trade walk (HISTORY.md 0200-boss E2b, `features/trade/model/stored`): one walk — its target (`hero:<id>` or `team:<ids>`; with a boss `team:<ids>|<boss>@<stage>|<id>*<★>,…` — another boss, stage or ★ is another walk, HISTORY.md 0200-boss E3 Q7) and the player's decisions (frozen slots, kept replacements, slots left empty, entered pieces) and ticks; kept until «Сделал» or «Отмена» (✕ keeps it; the same hero's or team's trade picks it up; another target replaces it); not in the backup.

`ogc.ingame` — «Надеть в игре» (`features/ingame`, HISTORY.md 0230): `{ v: 1, lines }`, a line per hero and slot with the record id and a snapshot of the piece; a malformed line, a second line of a slot or an unknown hero is dropped on read, and so is a dead line (the record no longer worn there) — on read and on every write; no lines — no key. Not written during a tour or when a newer page saved the gear; not in the backup.

`ogc.batch` — the batch («Партия»): entered pieces, «Не брать» keys and «Это другой» entries; kept until «Записать план» (Record the plan) or ✕. During a tour the batch is hidden and nothing is written to it (`persist = false`); without a roster scope («только мои» off or an empty roster) it is hidden too and the saved batch waits.

`ogc.gear` v3 also stores `worn` (equipped), `pin` (hero's pinned set), `crit` (hero → N, «сколько крита нужно герою»,
an integer 0…100; no entry — 100; [MODEL.md §12](MODEL.md)) `stars` (hero → transcend ★ 1…6, a fact about the hero;
no entry — the hero's minimum ★, the base rarity 1…3 (`game/hero/star` `heroStar`, owner 2026-10-12): a hero never has fewer; `Ctx.stars`), `lv` (hero → the white-stat level marked on the card, `100` or `120`; no entry — the settings default `lv120`; HISTORY.md 0205), `park` (ids of parked pieces, HISTORY.md 0200-boss E2b: a trade took them off and gave them to nobody; park ⊂ pooled and not worn — `syncWorn`; the verdict, reserves and the batch read pools without them — `gear:activePieces`; they travel with the record — drop / undo, Core Fusion) and `eff` (hero → `{typed, at}`: the stat-screen EFF the player typed and the app's
EFF then; the card shows the app's EFF × typed / at, «≈» once the app's EFF differs from `at`; HISTORY.md 0200-boss Q3). Invariants: worn ⊂ hero pool (`syncWorn` in
every mutation via `gc`); `pin`, `crit`, `stars`, `lv` and `eff` don't depend on the pool; Core Fusion moves `stars`, `crit`, `lv` and `eff` with the pieces (like `worn`; the other hero's own value wins) and lifts the pin (builds differ) — owner 2026-10-12, the hero who leaves keeps nothing; «Вернуть» moves them back only if nothing changed (`Switch` / `FusionFix` record what moved) — `dropChar` (and
«Вернуть» `undoDrop`; for a hero without pieces the star in the list or card does the same, with a message and «Вернуть»), an explicit "don't pin" / «Сбросить» clear them, and `normalizeStored` drops them for a hero outside the roster (`cleared`; an unknown id keeps all — owner 2026-10-12: a hero out of the roster has no data); a `crit` value that isn't an integer 0…100, a `stars` value that isn't an integer 1…6, an `lv` value that isn't exactly 100 or 120, or an `eff` entry that isn't two integers 1…9999, is dropped
on read (the read is then "not whole"). Fields of the old
model (`marks`, `autoNew`, `aim`, `pinned`) are read and discarded; a player from the old model is shown a one-time
message (`ogc.modelNote`; only for a v1/v2 store with pieces; its extra sentence about cleared marks, `ui.modelNoteMarks`, only when
the v2 store had `marks`, `aim` (a chosen build) or `pinned` («Не отдавать надетое») — v1 never counts). Backup — `OGC-GEAR9` (includes parked pieces: after a hero's worn slots a flag, then a bit per pool piece;
pinning, each hero's N other than 100: a flag and 7 bits, the stars: a flag and 3 bits, the typed EFF: a flag and two 14-bit numbers, and the hero's level: a flag and 1 bit, 0 — 100, 1 — 120), GEAR1–8 are readable.

**When the load-time normalisation is written back** (`features/gear/store/stored:readStored`). Roster and gear are read together
and normalized: Core Fusion (`fusion:normalizeStored` — X and Core Fusion X never together, X's pieces move to CF or are removed,
worn, stars, N, level and EFF move with them, the pin is lifted; the same runs on code import, v1 transfer and batch roster edits), "pieces only for roster
heroes" (everyone with pieces joins the roster), pin / N / ★ / level / EFF only for roster heroes (`cleared`, silent), v1/v2 → v3 and stale pins (`fixPins`). If anything changed — or a v1/v2 store
was upgraded or a pin moved — both keys are written at once, so the notice doesn't repeat on every launch and half of a fix
can't get lost. Deliberately **not** written when: a newer page version saved the gear (`newer`: this page doesn't understand it
and would erase it); there is no storage; the read dropped something (a substat not from the data, a mark or field of a newer
version, a string that doesn't parse — `readsWhole`): the page normalizes in memory and writes after the player's next action
(an old cached PWA with an older data snapshot would otherwise erase what the new one understands); a tutorial is running
(`holdStoredWrites`); nothing changed. Stale pins (the build vanished from outerpedia) are moved or dropped only on a whole read
and when the page's data is not older than what it has seen (`ogc.dataSeen`, outerpedia commit date): an old cached PWA has no
build from newer data, and a pin on it isn't stale.

**Two open tabs are out of scope** (owner, 2026-09-30): the app runs as one instance (split screen or a page next to the game).
`useGear` re-reads `ogc.gear` and `ogc.roster` on the `storage` event and when the page becomes visible again — so a PWA kept in
memory for hours doesn't overwrite another page's write blindly — and the normalisation write above runs on those re-reads too;
races between two tabs are not reviewed or fixed (a two-step action can be half-read and rewritten). If it ever matters: don't let
a second tab open, and write the normalisation only at load, not on the event.
