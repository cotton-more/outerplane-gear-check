# Автообновление данных

Раз в сутки GitHub Actions собирает сайт на свежих данных outerpedia, проверяет его и, если что-то изменилось,
открывает pull request с отчётом. **Сам робот ничего не публикует:** сайт обновится, только когда ты вольёшь PR
(с телефона — в приложении GitHub). Если ничего не изменилось, робот молчит.

```
ночью ─► собрать docs/ на свежем outerpedia ─► то же, что на сайте? ─► тишина (открытый PR закрывается)
                                              └► изменилось ─► проверки ─► PR с отчётом: обычный или черновик ⛔
                                                                            └► ты: Merge ─► сайт обновлён
сборка упала ─► issue «Автообновление: …» с логом (сайт не тронут)
```

Файлы: [`.github/workflows/data.yml`](.github/workflows/data.yml) (расписание: каждый день в 03:17 UTC),
[`scripts/autoupdate.sh`](scripts/autoupdate.sh) (сам прогон), [`scripts/check-data.mjs`](scripts/check-data.mjs) (проверки).

## Что приходит и что делать

| Что | Значит | Что делать |
|---|---|---|
| **PR «Данные outerpedia …»** | данные изменились, все проверки прошли | прочитать отчёт → Merge. Через 1–2 минуты сайт обновится, у игроков появится «Обновить» |
| **PR «⛔ Данные outerpedia …» в черновике** | данные изменились, но проверка нашла проблему; кнопка Merge недоступна | не вливать. Первая строка описания — причина. Дать ссылку на PR Claude (или разобраться самому) |
| **Issue «Автообновление: …»** | сайт даже не собрался: сеть, битый JSON, outerpedia поменяла формат так, что `update.py` падает | дать ссылку на issue Claude. Issue закроется сам, когда сборка снова пройдёт |
| тишина | данные те же, что на сайте | ничего |

**PR всегда один.** Пропустил обновление, а через неделю вышло ещё одно — робот не открывает второй PR, а пересобирает
тот же: ветка `data/auto` каждый раз заново строится от свежего `main`, а отчёт сравнивает с тем, что **опубликовано**,
так что в нём сразу всё накопившееся. Правил код в `main` за это время — следующий прогон соберёт данные уже на новом
коде, конфликтов не бывает. Опубликовал сам (`task publish`) или outerpedia откатила правку — PR закроется сам.

**Как чинится красный PR или issue.** В отчёте есть всё для разбора: какая проверка упала и на чём, ссылка на коммиты
outerpedia между опубликованной версией и новой (и какие из читаемых нами файлов в них менялись), команда, чтобы
воспроизвести у себя. Правка делается в `main` как обычно (обычно в `update.py`), потом Actions → «Обновление данных» →
**Run workflow** — робот пересоберёт PR на исправленном коде, не дожидаясь ночи. Если причина в самой outerpedia
(опечатка у них) и страница от неё не ломается — можно снять черновик кнопкой «Ready for review» и влить.

## Что проверяется

Почти все проверки **относительные**: старые данные прогоняются тем же новым кодом, и ошибкой считается только то,
чего раньше не было. Давно известные странности outerpedia (опечатка в одном билде) не краснят каждый прогон, новые — краснят.

1. **Разбор данных.** Новые предупреждения `update.py` и рекомендации, которые не удалось сопоставить с предметом, —
   против сборки опубликованных данных тем же кодом. Обычно это значит, что outerpedia поменяла формат.
2. **Ничего не пропало.** Персонажи, билды у персонажей, сеты и предметы из билдов; билдов не меньше чем на 10%.
3. **Ссылки в данных целы.** Билды ссылаются на существующие сеты, оружие, аксессуары, талисманы, сабстаты;
   у персонажей известные стихия и класс.
4. **Страница работает.** Собранный `docs/index.html` запускается в jsdom: пустой экран, разбор брони и оружия,
   карточка каждого персонажа — без исключений.
5. **Оценка на новых данных.** 800 тестовых предметов (входы эталона `test/golden.json`) оцениваются без ошибок,
   и каждый билд находит свою вещь: Legendary-броня его сета с его же первыми сабстатами получает «Оставить».
6. **Разница вердиктов** — не ошибка, а сведения: сколько вердиктов на тех же тестовых предметах изменилось и примеры.
   Больше 20% — предупреждение посмотреть внимательнее.

Ещё до проверок робот собирает **опубликованные** данные тем же кодом и сверяет с сайтом байт в байт: если на GitHub
сборка отличается от твоей на Mac, это issue, а не ложный PR каждую ночь.

Если код в `main` новее опубликованного, в отчёте есть раздел «Код приложения» со списком коммитов: при Merge они
выйдут вместе с данными.

Те же проверки запускает `task publish` (шаг `task check`): красные — публикация останавливается до коммита.

## Разовая настройка на GitHub

1. Settings → Actions → General → Workflow permissions → включить
   **«Allow GitHub Actions to create and approve pull requests»** (без этого робот не сможет открыть PR).
   Остальное (права на ветку, PR и issue) workflow запрашивает сам.
2. После пуша — Actions → «Обновление данных» → **Run workflow**, чтобы не ждать ночи и убедиться, что всё работает.
3. Уведомления о PR и issue приходят как обычно (почта, приложение GitHub) — репозиторий твой, ты на него подписан.

GitHub выключает расписание в публичном репозитории, если в нём 60 дней не было никакой активности, и заранее
присылает письмо. Включить обратно — Actions → «Обновление данных» → Enable workflow.

## Откат

Каждое обновление — отдельный коммит. В влитом PR кнопка **Revert** создаёт обратный PR; Merge — и через минуту-две
сайт на прежних данных, у игроков снова появится «Обновить». Следующей ночью робот опять предложит те же данные
(у outerpedia они никуда не делись) — не вливай, пока не разберёшься с причиной.

## Дальше, если PR окажутся стабильно скучными

Автослияние зелёного: все проверки прошли, ничего не пропало, вердикты почти не сдвинулись → PR вливается сам.
Пропажи, красные проверки, большой процент изменённых вердиктов по-прежнему ждут тебя. Пока не сделано.
