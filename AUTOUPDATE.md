# Автообновление данных — план (не сделано)

Сейчас данные outerpedia попадают на сайт, только когда кто-то запускает `task publish` на своём компьютере.
Пока инструмент личный, это нормально. Когда им пользуется гильдия, устаревшие билды — это неверные вердикты
у всех. Цель — чтобы свежие данные доходили до сайта без Mac, но **ничего не публиковалось без твоего решения**.

## Идея: робот не публикует, а предлагает

GitHub Actions раз в сутки собирает сайт на свежих данных и, если что-то изменилось, открывает pull request
с отчётом. Сайт обновляется, только когда ты нажмёшь Merge (с телефона — в приложении GitHub).

```
ночью ─► собрать docs/ на свежем outerpedia ─► ничего не изменилось? ─► тишина
                                              └► изменилось ─► проверки ─► PR с отчётом (зелёный / красный)
                                                                              └► ты: Merge ─► сайт обновлён
                                                                                     Revert ─► откат
```

Для публичного репозитория Actions бесплатны; прогон — пара минут.

## Что проверяется перед тем, как предложить

1. **Скачивание и формат.** Уже есть: `update.py` падает на ошибке сети, битом JSON, пропавшем файле,
   неизвестном sha коммита. Упал — PR не будет, придёт письмо о красном прогоне.
2. **Правдоподобие.** Сравнение с опубликованной версией (`diff_report` уже знает прошлые данные):
   персонажей, персонажей с билдами и билдов не стало заметно меньше; сеты и предметы массово не пропали.
   Пороги — в одном месте, как CFG. Нарушен порог — PR помечается красным, причина в описании.
3. **Страница работает.** Собранный `docs/index.html` открывается в jsdom (как `scripts/golden-old.mjs`)
   и без исключений оценивает набор тестовых предметов (входы эталона `test/golden.json`).
4. **Разница вердиктов.** На тех же предметах — сколько вердиктов изменилось против опубликованной версии,
   с примерами. Большой процент — повод посмотреть внимательнее, а не блокировка.

Описание PR: новые/пропавшие персонажи, изменённые билды, предметы и сеты (то, что сейчас печатает
`update.py`), итог проверок, «поменялось N вердиктов из M» с примерами.

## Что робот не может

- Писать прямо в `main` — только ветка и PR.
- Трогать код: коммит содержит только `docs/`.
- Публиковать без Merge (на первом этапе — вообще никогда).

## Что сделать до запуска

- [ ] **Пустые обновления.** Сейчас, если у outerpedia сменился только номер коммита, а билды и предметы те же,
      `docs/` всё равно меняется (метка `meta.commit`) — и у всех выскакивает «Обновить» зря. Так было
      25.09.2026 дважды (коммиты 5f177e7 и fbc2c4c). `same_content()` в `update.py` должна не смотреть на `commit`/`commitDate`,
      тогда и `task publish`, и робот такие обновления пропустят.
- [ ] **Одинаковая сборка на GitHub и на Mac.** Закрепить Node (`.nvmrc` + `engines` в package.json),
      один раз сверить: сборка в Actions побайтово равна локальной (`shasum` по `docs/`). Иначе каждую ночь
      будет ложный PR.
- [ ] **Лимит GitHub API.** Без токена — 60 запросов в час на IP, общий для раннеров. `update.py` должен
      брать `GITHUB_TOKEN` из окружения и слать `Authorization: Bearer …` в запрос sha коммита.
- [ ] **`task publish` подтягивает main.** Влитые PR появятся в `main` на GitHub — перед сборкой нужен
      `git pull --rebase`, иначе push отклонят.
- [ ] **Скрипт проверок** (`scripts/check-data.mjs`): пункты 2–4 выше, выход ≠ 0 и текст причины для описания PR.
- [ ] **Workflow** `.github/workflows/data.yml`: `schedule` (раз в сутки) + ручной запуск `workflow_dispatch`;
      `permissions: contents: write, pull-requests: write`; одна открытая ветка `data/auto`
      (новый прогон обновляет её, а не плодит PR).

## Этапы

1. **Только PR.** Всё решаешь ты.
2. **Автослияние зелёного** — когда PR стабильно скучные: все проверки прошли и ничего не пропало → вливается
   сам. Пропажи, красные проверки, большой процент изменённых вердиктов — по-прежнему ждут тебя.

## Откат

Каждое обновление — отдельный коммит. Кнопка Revert в влитом PR создаёт обратный PR; Merge — и через
минуту-две сайт на прежних данных. У игроков снова появится «Обновить» и вернёт прошлую версию.
